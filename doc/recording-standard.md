# 文档记录规范

## 1. 强制原则

1. 记录事实和学习过程，不写无法追溯来源的结论。
2. 一次实验、一项问题或一次技术决策各使用一个文件；不要写成按日期堆叠的流水账。
3. 知识笔记解释“它是什么、为什么”；实验记录“做了什么、看到了什么”；问题记录“如何定位”；当前状态只做摘要并链接详情。
4. 原始命令、输出和错误不得为了“看起来正确”而修改。过长日志可截取关键部分，但必须说明省略范围并保存原文件位置。
5. 密钥、令牌、序列号和个人信息必须脱敏。禁止记录或提交无法公开的厂商资料。

## 2. 文件与时间格式

- 文件名使用小写英文、数字和连字符，例如 `uboot-boot-flow.md`。
- 实验编号：`EXP-YYYYMMDD-NNN`；问题编号：`ISSUE-YYYYMMDD-NNN`；决策编号：`DEC-YYYYMMDD-NNN`。
- 日期使用 `YYYY-MM-DD`；需要精确时间时使用 ISO 8601，并标注 `+08:00`。
- 图片和附件统一放在 Vault 根目录的 `_assets/`，文件名应包含主题和内容，例如 `serial-console-r1-wiring.jpg`；正文使用相对 Markdown 路径引用。不得直接粘贴为无意义名称。

## 3. 必填元数据

除目录索引外，每篇记录必须以如下 YAML 开头：

```yaml
---
title: "准确描述内容的标题"
type: note | experiment | issue | decision | review | tool | environment | status
status: draft | active | blocked | verified | resolved | archived
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags: [rk3588]
related: []
---
```

`updated` 必须随实质内容变化更新。`verified` 表示结论已有证据且可复现；不能因为命令无报错就直接标记为 `verified`。`resolved` 仅用于问题，且必须记录根因和回归验证。可选属性 `aliases` 用于记录英文缩写、中文译名或常见别名，避免为同一概念重复建笔记。

工具记录使用 `templates/tool.md`，必须写明运行端、安装来源、已验证版本、最小验证命令、权限要求和风险；尚未实际执行的高级用法不得写成已验证。

## 4. 链接与知识关联

- 正文内部链接使用相对 Markdown 链接，以便在 Obsidian、Git 托管页面和普通编辑器中查阅。
- `related` 属性必须使用加引号的 Obsidian 内部链接，并从 Vault 根目录定位，不写 `.md`，例如：

```yaml
related:
  - "[[experiment/exp-20260807-002-boot-linux-via-debug-uart]]"
  - "[[issue/issue-20260807-001-maskrom-and-linux-boot]]"
```

- `related` 只表达直接关系。知识笔记应关联验证实验；问题应关联支撑假设或结论的知识笔记和实验；同一事实只保留一个主记录。
- 每个目录的 `*-index.md` 是内容地图，负责按主题或状态导航。新增记录后必须同步更新所属索引。
- 移动或改名应在开启“自动更新内部链接”的 Obsidian 中进行；批量修改后必须检查失效链接。

## 5. 证据等级

重要信息必须在正文中标明来源：

- **已验证**：由本机命令、板卡日志或重复实验直接证实。
- **用户提供**：由学习者描述，尚未通过实验核对。
- **资料记载**：来自可定位的官方资料，必须附标题、版本和链接。
- **推测**：基于现象提出的假设，必须写明验证办法。
- **待确认**：缺少必要信息，禁止作为后续危险操作的依据。

推测只有在证据支持后才能改为结论；被否定的假设不要删除，应记录否定证据。

## 6. 命令、日志与实验

每组命令必须记录执行端（Arch 主机、U-Boot 或目标 Linux）、当前目录、必要版本和关键参数含义。输出后记录退出码；涉及块设备时必须保存操作前后的 `lsblk` 等识别证据。实验必须包含目标、前置条件、步骤、预期、实际结果和结论。改变系统状态的命令还应写明影响范围、备份及恢复方法。

`/tmp` 只用于一次性中转或转换，重启后可能清空，不能作为可复用证据的唯一位置。可由命令重新生成、但需要跨重启保留的本机分析产物放在 Git 忽略的 `build/local/`；正文记录来源、命令、大小和校验值。只有完成脱敏且确有长期查阅价值的原始日志或附件放入 `doc/_assets/`。

## 7. 问题生命周期

问题状态依次使用 `active`、`blocked`、`resolved` 或 `archived`。问题记录必须包含：可观察现象、复现条件、最近变更、影响范围、假设列表、逐次验证、根因和回归验证。每次只改变一个主要变量。没有证据时写“原因未知”，不得用临时绕过方案冒充根因。

## 8. 更新流程

一次有效学习或排障结束后，按顺序执行：

1. 保存实验和问题证据。
2. 将已验证且可复用的认识整理到知识笔记。
3. 更新问题状态及关联链接。
4. 更新 `status/current.md` 的完成项、阻塞项和唯一明确的下一步。
5. 达到阶段完成标准时填写阶段复盘，并更新学习路线。

任何“完成”都必须链接到实验、日志、代码或复盘证据。多个文档描述同一事实时，指定一个主记录，其他位置只写摘要和相对链接。

## 9. 状态变更历史

`status/current.md` 是当前快照，`status/history.md` 是追加式历史。阶段、任务、问题或阻塞项的状态发生变化时，必须记录：记录时间、事件发生时间、对象、原状态、新状态、原因、证据和信息来源。记录时间使用 ISO 8601；事件时间未知时明确写“未知”，不得倒推或伪造。

历史条目不得覆盖或静默删除。之前的记录有误时，新增“更正”条目并链接原记录。文字补充但状态未变化时只更新主文档，不创建虚假的状态转换。

## 10. Agent 记录边界

Agent 可以整理用户提供的信息和已执行命令，但不得虚构实验输出、板卡状态或掌握程度。Agent 应保留学习者的排障思路，并通过提问补全缺失信息。尚未亲自验证的 Agent 建议只能标记为“推测”或“待验证”，不能写入最终结论。
