# DEC-20260813-003 NPU 上运行 LLM 作为项目核心

## 背景与约束

学习者要求项目必须让 R1 的 NPU 实际运行 LLM；仅把操作系统换到开发板、或由主机/MCP 运行模型，不能体现本项目价值。目标时间为 2026 年 9 月下旬。R1 为 4 GB RAM 的 RK3588S，当前厂商 Ubuntu 5.10 系统的 `rockchip.service` 曾因缺少 `/rknpu2-rk3588-*.tar` 失败，因此 NPU 运行时、可用模型格式和内存余量均未验证。

## 候选方案

| 方案 | 优点 | 缺点 | 风险 | 验证情况 |
| --- | --- | --- | --- | --- |
| CPU 或主机运行 LLM，R1 仅采集数据 | 快速 | 不满足 NPU+LLM 要求 | 简历表述与实际能力不符 | 未采用 |
| R1 NPU 运行小型量化 LLM，作为板端服务核心 | 满足核心要求，可展示部署、性能与系统集成 | 受厂商运行时、模型格式和 4 GB 内存限制 | 当前运行时可能不完整 | 选定，待验证 |
| 先完成 Linux+Zephyr AMP 再接入 LLM | 与长期目标最接近 | 7 周内并发风险过高 | NPU、启动、AMP 三条不确定链相互阻塞 | 保留为后续扩展 |

## 决定

近期综合项目采用“**R1 NPU LLM 边缘事件助手**”：R1 上的常驻 Linux 服务采集受控系统/传感器事件，调用板端 NPU LLM 生成结构化分析或告警结果，并以 systemd 管理。验收必须保留以下证据：模型和运行时来源、NPU 实际执行证据、内存占用、首 token/完整响应延迟或等价性能指标、可重复启动与一个可控输入样例。

LLM 的具体名称、量化格式、Rockchip 运行时及是否使用 NPU 均不得预设；先完成只读兼容性调查再选择。若当前厂商栈不可用，先定位缺失组成与可恢复路径，再决定是否引入经来源和校验确认的厂商 SDK。到期项目不承诺完成 Zephyr AMP；AMP 决策仍是长期路线，NPU LLM 项目应为其提供 Linux 侧工作负载和观测基础。

## 执行方式

采用“**项目牵引、按需下钻**”的学习方式：先完成一条最小垂直链路（运行时识别 → NPU LLM 单次推理 → 板端服务 → 可控演示），优先复用现有内核驱动、厂商运行时和用户空间接口。只有链路被某个具体问题阻断时，才围绕该问题补学日志、systemd、设备树、驱动源码或自行实现缺失部分；不再把逐行读完驱动作为项目开工前提。

## 影响与复查条件

- 影响：暂停逐行深挖当前 GPIO 驱动样本；保留设备树、服务、日志、内存和进程等直接支撑部署与排障的学习。阶段 5 立即进入“运行时可用性验证”，阶段 6 的最小范围以上述常驻服务为准。
- 何时需要重新评估：NPU 运行时缺失且没有可确认的恢复/安装路径；任一候选模型在 4 GB 设备上无法稳定加载；或测量表明推理未实际使用 NPU。
